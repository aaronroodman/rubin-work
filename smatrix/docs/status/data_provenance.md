# batoid_rubin data — provenance and what is recoverable

> **Status:** current · **Last updated:** 2026-09-07 · **Kind:** working state (data inventory)

The `smatrix` work reads four dataset directories under `$BATOID_RUBIN_DATA_DIR`. They
differ sharply in how recoverable they are, which matters because two of them are outputs
of local pipelines rather than downloads.

| directory | size | origin | recoverable? |
|---|---|---|---|
| `fea_legacy/` | 32 M | Zenodo DOI **8384326** | yes — re-download |
| `bend/` | 68 M | Zenodo DOI **8384775**, 20 AOS bending modes per mirror | yes — re-download |
| `bend_full/` | 291 M | generated by [`../../code/build_full_modes.py`](../../code/build_full_modes.py) from `fea_legacy`; 156 M1M3 + 72 M2 modes | **yes — regenerated on S3DF 2026-09-07, ~2 min** |
| `bend_zemax/` | 285 M | generated by the ZEMAX pipeline (below); ZEMAX/OFC basis, 153 M1M3 + 69 M2 | **not present here — regenerable, see below** |

`download_rubin_data.py`, shipped inside the installed `batoid_rubin` package, knows five
Zenodo datasets: `bend_legacy`, `fea_legacy`, `bend`, `bend_ptt`, `ccd_height_map`.
**`bend_full` and `bend_zemax` are not among them** — they are not upstream products, and
no clone or download will produce them.

## `bend_zemax` is absent here, but is now regenerable

It is not in `$BATOID_RUBIN_DATA_DIR` on S3DF, which holds only `bend/`, `bend_full/`,
`ccd_height_map/`, `fea_legacy/` and a stray top-level `bend.yaml`. It is also not an
upstream product, so no download produces it — it has to be rebuilt.

The six scripts that build it are committed at
[`../../code/zemax_build/`](../../code/zemax_build/), whose `README.md` gives the run
order, the flags and the intermediates. In outline:

```
M1M3_match_forces.py    → M1M3_decompose_sag.py    → M1M3_format_for_batoid.py
M2_match_forces.py      → M2_decompose_sag.py      → M2_format_for_batoid.py
```

Every input is recoverable: the FEA data comes from three public repos
(`bxin/ZEMAX_FEMAP`, `lsst-so/M1M3_ML`, `lsst-so/M2_FEA`), and `ZEMAX_FEMAP` is cloned at
`/sdf/group/rubin/u/roodman/LSST/packages/ZEMAX_FEMAP`, which the scripts' `--indir`
defaults now find via `$ZEMAX_FEMAP_DIR`. The stage-1 `M1M3_NASTRAN.asdf` is itself a
product of `M1M3_match_forces.py`, not a delivery, so nothing in the chain depends on a
file that exists in only one place. All six scripts have been confirmed to start on the
USDF with `asdf` installed (`pip install --user asdf`).

## Separately: `tmmax` in `filters/`

`filters/` needs [`tmmax`](https://github.com/bahremsd/tmmax), which is not in the S3DF
stack environment. It is **installed** now, under
`~/.local/lib/python3.13/site-packages/tmmax`, and imports resolve.

It must be installed **with `--no-deps`**:

```bash
pip install --user --no-deps tmmax
```

The reason matters, and applies to any reinstall. `tmmax` is JAX-based, and the stack
already ships JAX 0.10.2 which
**four `optatmo/` modules depend on** (`config.py`, `data_fit.py`, `fit_monitor.py`,
`fit_optatmo.py`). A full-dependency install could pull an incompatible JAX that shadows
the stack's and break `optatmo/`.

`--no-deps` is sufficient because `filters/` barely uses the package:

- `thinfilm.py:20` needs only `__import__("tmmax").__file__` to locate the bundled
  `nk_data/numpy` refractive-index tables — no solver, no JAX.
- `validate_engines.py:44` imports `tmmax.tmm` as an optional cross-check inside a
  try/except, and that file's own docstring records that **`tmmax` is broken for
  multilayers** and is deliberately not used as the engine; `tmm_fast` is. So a skipped
  check costs nothing.

In other words `tmmax` is installed here as a **data source**, not a solver. Do not
"fix" it by installing the full dependency tree.

## Two things to review in `$BATOID_RUBIN_DATA_DIR`

### Top-level duplicates — CLEANED 2026-09-07

The data directory used to carry 14 files at its top level that were byte-identical
(md5-verified) to copies inside `bend/`, costing ~68 M. Aaron deleted them. The directory
now holds only `bend/`, `bend_full/`, `ccd_height_map/`, `fea_legacy/` and a leftover
top-level `bend.yaml` (still an exact duplicate of `bend/bend.yaml`, harmless).

Verified after the cleanup: `load_bend` works for both `bend` (20 modes) and `bend_full`
(156 modes). Nothing read the top-level copies — `load_bend` takes an explicit `bend_dir`
and `LSSTBuilder` defaults to the bare string `"bend"`.

### `camera_gravity.py` now picks a different bending basis

`aos/code/static_optics/camera_gravity.py:95` searches for a bend directory in the order
**`bend_zemax` → `bend_full` → `bend`**, taking the first that exists. Before 2026-09-07
only `bend` existed on S3DF, so it used that. Now that `bend_full` has been regenerated
here, the same code silently selects `bend_full` instead — a different basis (156 M1M3 +
72 M2 modes rather than 20 per mirror).

Its own docstring says gravity does not use the bending-mode basis, so the result may be
unaffected, but this has not been verified. Check before trusting a camera-gravity output
produced after that date, and see [`rerun_needed`](../../../aos/docs/status/rerun_needed.md).
