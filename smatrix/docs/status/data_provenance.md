# batoid_rubin data — provenance and what is recoverable

> **Status:** current · **Last updated:** 2026-09-07 · **Kind:** working state (data inventory)

The `smatrix` work reads four dataset directories under `$BATOID_RUBIN_DATA_DIR`. They
differ sharply in how recoverable they are, which matters because two of them are outputs
of local pipelines rather than downloads.

| directory | size | origin | recoverable? |
|---|---|---|---|
| `fea_legacy/` | 32 M | Zenodo DOI **8384326** | yes — re-download |
| `bend/` | 68 M | Zenodo DOI **8384775**, 20 AOS bending modes per mirror | yes — re-download |
| `bend_full/` | 291 M | generated by [`../../code/build_full_modes.py`](../../code/build_full_modes.py) from `fea_legacy`; 156 M1M3 + 72 M2 modes | **yes — regenerated on S3DF 2026-09-07, ~2 min** |
| `bend_zemax/` | 285 M | generated by the ZEMAX pipeline (below); ZEMAX/OFC basis, 153 M1M3 + 69 M2 | **no — see below** |

`download_rubin_data.py`, shipped inside the installed `batoid_rubin` package, knows five
Zenodo datasets: `bend_legacy`, `fea_legacy`, `bend`, `bend_ptt`, `ccd_height_map`.
**`bend_full` and `bend_zemax` are not among them** — they are not upstream products, and
no clone or download will produce them.

## `bend_zemax` has no recovery path

It is produced by six scripts that exist in exactly one place, `/Users/roodman/LSST/zemax_build/`
on the laptop, run in this order (per [`../plots.md`](../plots.md)):

```
M1M3_match_forces.py    → M1M3_decompose_sag.py    → M1M3_format_for_batoid.py
M2_match_forces.py      → M2_decompose_sag.py      → M2_format_for_batoid.py
```

Input `M1M3_NASTRAN.asdf`; intermediates `M1M3_decomp.asdf` (408 M) and `M2_decomp.asdf`
(92 M). Those scripts are **not** in this repository, **not** in the installed
`batoid_rubin` (which ships only `builder.py`, `utils.py`, `visualize.py` and the data
downloader), and sit untracked inside a git repository that has no commits and no remote.

## What this means for the code

Four scripts read `bend_zemax` and so cannot run on S3DF until it is copied or
regenerated: `full_normalization.py`, `make_normalization.py`, `mode_gallery_full.py`,
`plot_b52.py`. Their paths are correct — they resolve `$BATOID_RUBIN_DATA_DIR` — but the
data is absent.

`thermal_sensitivity.py`, `mode_gallery.py`, `validate_normalization.py` and
`build_full_modes.py` need only `fea_legacy` and `bend`, both present, and work here.

## Separately: `tmmax` in `filters/`

`filters/` needs [`tmmax`](https://github.com/bahremsd/tmmax), installed on the laptop
with `pip install --user` but not present in the S3DF stack environment. The throughput
paths are fixed and resolve; the imports fail until it is installed.

**Install it with `--no-deps`:**

```bash
pip install --user --no-deps tmmax
```

The reason matters. `tmmax` is JAX-based, and the stack already ships JAX 0.10.2 which
**four `optatmo/` modules depend on** (`config.py`, `data_fit.py`, `fit_monitor.py`,
`fit_optatmo.py`). A full-dependency install could pull an incompatible JAX that shadows
the stack's and break `optatmo/`.

`--no-deps` is sufficient because `filters/` barely uses the package:

- `thinfilm.py:20` needs only `__import__("tmmax").__file__` to locate the bundled
  `nk_data/numpy` refractive-index tables — no solver, no JAX.
- `validate_engines.py:44` imports `tmmax.tmm` as an optional cross-check inside a
  try/except, and that file's own docstring records that **`tmmax` is broken for
  multilayers** and is deliberately not used as the engine; `tmm_fast` is. So a skipped
  check costs nothing.

In other words `tmmax` is installed here as a **data source**, not a solver. Do not
"fix" it by installing the full dependency tree.
